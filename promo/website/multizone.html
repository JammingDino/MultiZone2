Movement II

B

Divisi.

— one part splits into several, and comes back together

Perspective mode shows you every model's answer. Multizone mode resolves them into one. A zone flagged as a Response Leader doesn't answer from its own knowledge — it spawns a panel of sub-agent zones, briefs each one on a deliberately opposing angle rather than forwarding your message, cross-examines them against each other, and only then writes a single synthesised answer.

    The brief

    bar 18

    Forwarding your question would have got you four of the same answer.

    That is the whole difference. Ask four capable models the same question and you get four capable answers that agree, because they were trained on overlapping ground and you gave them identical framing. The leader writes each sub-agent a different starting assumption, and an agent told to assume the deploy is innocent goes looking somewhere the other three never will.

    The panel above found four things. Three turned out to be one fault seen from different distances, and the fourth was a separate real problem nobody asked about. No single member had all of it.

    While a leader is driving them, sub-agents can't reach you. Their ask_user calls are suppressed — a question raised in a chat nobody is watching would wait forever. That is a real constraint, not a detail: anything a sub-agent must ask about will stall, which is why the approvals section below matters before a long run.

    Tools

    simultaneamente

    Sub-agents don't have to run one at a time.

    spawn_subagent and send_subchat_message both take background: true, which returns the subchat id immediately and runs that sub-agent on its own task. A leader can put five specialists to work in a single message, keep reading code while they think, and pick every reply up later.

    ToolWhat it does
    spawn_subagentStart a sub-agent on a named zone with a brief of the leader's own writing. With background: true it returns the subchat id at once instead of waiting.
    send_subchat_messagePut a follow-up to a sub-agent already running — the cross-examination step. Also backgroundable.
    collect_subagentsPick up every backgrounded reply once the leader is ready for them.
    list_subchatsThe sub-agents this conversation already has. The leader is told to continue one rather than re-brief a fresh copy.

    Stopping the chat stops its background sub-agents with it.

    The whole call tree, inline

    Talk to a sub-agent yourself

    Open a subchat and it takes messages like any other chat, exports like any other chat, and can ask you a question, because now you are the one who sent.

    Exports keep them

    Sub-agent conversations nest under the turns that spawned them in both Markdown and PDF, each turn attributed to the zone that wrote it, so a prompt from the leader is never presented as something you asked for.

    Turn the nesting off under Settings → Appearance → Chat export when you only want the conversation you were part of.

    Teamwork

    insieme

    bar 60

    Working one codebase together.

    Sub-agents have always had the real tools — read, write, search, shell, and they inherit the parent chat's project directory. What they lacked was any way to know the others existed, which left two safe patterns: run them one at a time, or have them hand patches back for someone else to apply. Agents working against each other, carefully sequenced.

    The teamwork tool group is the coordination layer that lets them work alongside each other instead. Press run and watch what happens when two of them reach for the same file.

    Tool calls

      The session board post_note / team_status

      • Nothing posted yet. The board is where decisions travel with the edits that caused them.

      claim_files

      An advisory lock on the files an agent is about to edit, with a stated intent. A write to a file another agent holds is refused by the tools, so a claim isn't a convention someone can forget. An unclaimed write auto-claims, so the protection holds even for a zone that never calls the tool, and claims expire, and release when the agent's turn ends, so a crashed agent can't own a file forever.

      post_note · team_status

      The session's shared board. Parallel edits only compose if the decisions travel with them — “parse() returns None now instead of raising” has to reach whoever is editing the caller, and one sub-agent can't read another's transcript.

      Reads are never blocked, and an ordinary single-zone chat never touches any of it.

      Zone teams

      tutti

      Seven zones. One model. Seven temperatures.

      Some presets only work as a set, so the library's Teams section installs one in a single action — a leader plus the specialists it delegates to, all bound to your default model. The shipped Code Team is a general codebase collaboration: talk to Code Team Lead like a colleague about a symptom, a feature, or a piece of code that annoys you, and it runs the team over your project.

      1. leadCode Team LeadClarifies the ask, writes the contract the others must honour, splits the work into file-disjoint slices, and picks the winner in compete mode.
      2. 0.30Code ScoutMaps the ground first. Reads only — a scout that could edit is a different permission policy.
      3. 0.15Code Implementer · CarefulThe conservative attempt. Edits its own slice at the same time as the inventive one.
      4. 0.85Code Implementer · InventiveThe other attempt, at the other end of the temperature range. Same contract, different instincts.
      5. 0.40Code Test AuthorWrites the tests against the same contract, in parallel with the implementers rather than after them.
      6. 0.55Code ReviewerAttacks the result. Adversarial by construction, not by mood.
      7. 0.25Code VerifierRuns the builds and the suites on the combined tree — the part where an opinion becomes evidence.

      Compete mode

      For a hard bug the lead switches the shape: both implementers attack the same problem independently, hand back diffs, and the leader picks on test evidence rather than on argument. Seven zones on one model at seven temperatures — the value comes from independent attempts and adversarial review, not from a bigger model.

      Before a
      long run

      practical

      A sub-agent cannot show you a prompt.

      Which means anything it must ask about will simply stall. Raise Task length to 60 or more, then deal with approvals properly — since 0.14.0 that no longer means turning the safety off wholesale.

      1. Set policy by kind of work

        Under Settings → Chat → By kind of work, set read, web and sub-agents to Auto and leave shell on Ask. The zone editor has the same controls per zone, which is how a scout that only reads and an implementer that may edit stop being the same policy.

      2. Allow the commands you actually want run

        Add them beside it — npm run test, git status. An allow list of specific commands is a much smaller grant than switching shell approvals off.

      3. Draw the boundary in paths

        Where edits may land (0.14.5) is the same idea over the filesystem. Put {project} in the allow list and edits inside whichever project the chat is in stop prompting, while anything outside it still asks. A list here is a boundary rather than a shortcut — being asked about exactly those is the reason to draw one.

      4. Give the team a memory

        Shared memory at project scope is the durable counterpart to the board: how this repo's tests are run, or a trap someone hit, is injected into every agent on the project, including the ones spawned next week.
